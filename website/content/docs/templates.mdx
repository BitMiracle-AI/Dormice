---
title: Templates
description: Learn how to create sandboxes from your own Docker images by registering them as templates.
---

A template is a name pointing at a [Docker
image](/docs/core-concepts#containers-and-images) — the read-only
snapshot a sandbox starts from. Register your own image as a template
and sandboxes created from it come with your tools preinstalled.
Dormice deliberately has no build pipeline — the host's Docker daemon
is already an image store, and `docker build` is already the build
tool.

**Never built a Docker image?** The three-line version: you write a
`Dockerfile` — a recipe that starts from an existing image and adds
your tools (`FROM ubuntu:24.04`, then `RUN apt-get install …`) — and
`docker build -t name:v1 .` bakes it into an image tagged `name:v1`.
The `:v1` part is the tag: a version label you choose. Docker's own
[getting-started guide](https://docs.docker.com/get-started/) covers
the rest.

## Create a template

Build an image (any way you like), push it to the fleet's image
registry, and register its name:

```sh
docker build -t my-agent-env:v1 .
docker tag my-agent-env:v1 <registry address>/my-agent-env:v1
docker push <registry address>/my-agent-env:v1     # user dormice, password = the API token
dor template add my-agent-env my-agent-env:v1
dor template ls
```

The template names the **bare** image (`my-agent-env:v1`), never the
registry-prefixed one: a node that lacks the image pulls it from the
fleet's registry — prefixing the address itself, and tagging it back
under the bare name — the moment a configuration bundle names it (ahead
of any sandbox needing it) and again at creation if it is still missing.
The registry address is on the console's settings page
(`DORMICE_REGISTRY_ADDRESS` in the gateway's env). A fleet of one machine
can skip the push: the image is already on the only node. An image whose
name carries its own registry (`ghcr.io/you/tool:v1`) is pulled from
there as written.

## Create sandboxes from a template

Both API surfaces accept a template name at creation:

```ts
// Native: a creation-time option, like policy
await client.acquireSandbox('user-42', { template: 'my-agent-env' });

// E2B: the templateID argument
const sbx = await Sandbox.create('my-agent-env', { /* the two URLs + apiKey */ });
```

An unknown template name is refused — 400 natively, 404 through the E2B
surface — never silently substituted with the base image.

## Update a template

Re-registering a name points it at a new image. Existing sandboxes
converge onto it on their next wake from any cold state — frozen,
stopped, or archived — each paying one container swap (a few seconds, no
image pull) the first time, then back to millisecond wakes:

```sh
docker build -t my-agent-env:v2 .
dor template add my-agent-env my-agent-env:v2  # re-registering re-points the name
dor sandbox rebuild user-42                    # optional: swap one sandbox NOW, don't wait for its next wake
```

A running sandbox is never touched behind its back: the swap happens
only when the sandbox is next woken (or explicitly rebuilt). Through the
swap, `/home/user` carries over untouched and everything outside it
resets onto the new image — including any processes a frozen sandbox
had alive, which is within the platform's crash-only contract (sandboxed
code must survive its container being replaced anyway). See
[Rebuild a sandbox](/docs/persistence#rebuild-a-sandbox).

Removing a template's registration follows the same rule: its sandboxes
converge onto the daemon's base image at their next cold wake.

You can ask which sandboxes still run an old image with the
`listSandboxImages` verb (SDK method of the same name), or look for the
"upgradable" marker in the [console](/docs/console)'s sandbox list.

**Note:** the comparison is by image name. Rebuilding the same tag in
place is invisible to it — upgrade by registering a new tag
(`my-agent-env:v2`), not by overwriting `v1`.

## Remove a template

```sh
dor template rm my-agent-env
```

Removing a template that sandboxes still use is refused with a 409
naming a sandbox. Removing an unknown name is a no-op, and removing a
registration never removes the image itself.

## Image requirements

Sandboxes mount their own disk over `/home/user` (see
[Anatomy of a sandbox](/docs/architecture#anatomy-of-a-sandbox)), so a
template must
install its tools into image paths (`/opt`, `/usr/local`) — anything
baked under `/home/user` is hidden at runtime. The stock image's
[`Dockerfile`](https://github.com/BitMiracle-AI/Dormice/blob/main/images/Dockerfile)
is the reference: layers ordered by change frequency, tools outside the
home directory, non-root user at uid 1000.

## Good to know

- **Registration is configuration.** The image is not checked for
  existence when you register — register first, build later, if you
  like. A node that lacks the image pulls it from the fleet's registry;
  if the registry lacks it too, creation fails with a named error
  (`image X is not on this host, and pulling <registry>/X from the fleet
  registry failed … — push it from a machine that has it: docker login
  <registry> -u dormice (the password is the fleet token), then docker
  tag X <registry>/X && docker push <registry>/X`).
- **`base` is reserved.** Through the E2B surface, `Sandbox.create()`
  with no template argument means the fleet's base image (a setting on
  the console's settings page); the name `base` cannot be registered.
- **Templates apply at creation only.** An acquire with a `template` on
  a name that already has a sandbox keeps the sandbox it finds, template
  unchanged — but an unknown name is still refused, never silently
  ignored.
